### 前言

过去两年里，AI Coding 的体验很容易让开发者产生一种错觉：软件工程中的复杂性终于被消灭了。

输入一段自然语言，模型便能生成一个函数；描述一个需求，Agent 便能在仓库里修改多个文件；如果再接上终端、测试、搜索、GitHub，它看起来甚至像一个不会疲惫的初级工程师。过去需要查文档、读源码、搭环境、写样板代码的过程，现在被压缩成了几轮对话。

这当然是令人兴奋的。对于开发者来说，AI Coding 的价值并不只在于“少敲几行代码”，而是它降低了进入某些技术领域的门槛。学习 Rust 时，它可以给出比初学者更规范的代码；写一些熟悉框架下的 CRUD，它可以快速补全那些机械重复的部分；面对陌生 API，它至少能给出一个大致方向。

但越是使用它，越会发现另一个问题：它并不是稳定地“理解”了整个软件系统，而是在大量上下文、概率模式、代码片段和工具反馈之间寻找一个看似合理的输出。

这就引出了 AI Coding 中最难被忽视的问题：幻觉。

很多人谈 AI 幻觉时，会想到模型编造事实、虚构论文、杜撰引用、把不存在的人名和事件说得煞有介事。但在 Coding 场景中，幻觉并不总是表现得这么明显。它可能不是一本不存在的书，而是一个不存在的 API；不是一个错误的历史年份，而是一个错误的参数顺序；不是一段胡编乱造的解释，而是一段局部可运行、整体却埋雷的代码。

这也是我想讨论的问题：当大语言模型进入软件工程以后，幻觉到底变成了什么？它为什么会发生？它会给 Coding 带来什么影响？以及我们应该如何与这种能力共处。



### 什么是幻觉？

如果用一句话概括，幻觉就是：模型输出了一个看起来合理，但缺乏事实、上下文或系统约束支撑的内容。

在普通文本场景下，这种不一致通常发生在事实层面。例如模型把某篇论文的结论说错，把某个开源项目的作者说错，或者编造一个根本不存在的链接。它的问题在于：语言非常流畅，语气非常确定，但内容并不可靠。

这正是大语言模型最迷惑人的地方。它不是像传统程序那样报错、崩溃、返回空值，而是会继续生成一段语法正确、结构完整、语气自信的答案。对于读者来说，如果缺少相关背景知识，很难在第一时间意识到它错了。

从模型机制看，这并不神秘。大语言模型本质上是在给定上下文中预测下一个 token。它优化的是局部条件概率，而不是现实世界中的事实正确性。一个 token 在当前上下文里概率很高，并不意味着它对应的事实是真的；一整段话在语言分布上非常自然，也不意味着它在现实世界中成立。

这就像一个人参加考试时，试卷要求他必须写满答案，而评分体系又更奖励“看起来像标准答案”的表达。久而久之，他会更倾向于猜测，而不是承认自己不知道。

幻觉并不是模型偶尔发疯，而是这个生成机制在开放世界任务中的自然副产物。

更麻烦的是，后训练和产品交互还会进一步强化这种倾向。用户通常更喜欢模型“有帮助”，而不是模型频繁回答“不知道”；评测基准也经常奖励正确答案，却没有充分奖励合理拒答。于是模型被训练成了一个更愿意输出答案的系统，而不是一个稳定知道自己边界的系统。

这也是为什么“幻觉”不是一个单点 bug。它不是简单地调小 temperature、换一个 prompt、升级一个模型就能彻底解决的问题。它来自训练数据、参数记忆、上下文窗口、解码策略、后训练目标和产品评估方式共同构成的系统。



### Coding 中的幻觉为什么更隐蔽？

代码和普通文本有一个很大的不同：代码可以执行。

这看起来似乎是好消息。文本的真假需要外部知识验证，而代码至少可以通过编译器、类型检查器、单元测试和运行结果来判断。某种意义上，代码比自然语言更容易被验证。

但这只是问题的一半。

代码确实更容易得到“局部判定”，却更难得到“完备判定”。一个函数能通过单测，不代表它满足真实业务需求；一个补丁能编译，不代表它不破坏已有功能；一个 API 调用没有语法错误，不代表它在当前依赖版本下是推荐用法；一个服务能启动，不代表它在高并发、异常重试、网络抖动和资源耗尽时仍然可靠。

这就导致 AI Coding 中的幻觉经常不会以“明显错误”的方式出现，而是以“局部正确”的方式出现。

例如：

1. 它生成了一个看似存在的包名，但项目里并没有这个依赖。
2. 它调用了一个真实存在的 API，但参数顺序或语义理解错了。
3. 它补全了一个函数，却忽略了调用方对错误码、返回值、幂等性的约定。
4. 它修复了当前测试失败的问题，却破坏了另一条没有被测试覆盖的路径。
5. 它写出了一段能跑的代码，但引入了并发竞态、资源泄露或安全漏洞。
6. 它按自己的理解重构了模块，却不符合这个仓库已有的抽象边界。

这些问题都很像传统意义上的 bug，但它们又带有明显的幻觉特征：模型并不是基于完整事实和完整约束生成代码，而是在局部上下文中补出了一个“像这个项目会有的东西”。

这比文本幻觉更危险，因为代码会进入系统运行。一段错误解释最多误导读者，一段错误代码却可能变成线上事故。



### 从局部概率最优到模块化局部最优

我更愿意把 AI Coding 中的一类典型幻觉称为：模块化局部最优幻觉。

它的意思是：模型在某个局部上下文下生成了看起来最合理的代码，但这段代码放回完整系统后并不是全局最优，甚至不是正确解。

这和普通文本中的“局部概率最优不等于全局事实最优”是同构的。

在文本生成中，模型每一步都在预测下一个 token。某个错误 token 一旦被选中，后续内容就会围绕这个错误前缀继续展开，最后形成一整段自洽但错误的答案。

在代码生成中，情况更复杂。模型不仅要预测 token，还要满足函数、类、模块、仓库、依赖、测试、部署环境以及业务约束。它生成的不是一段孤立文本，而是系统中的一部分。

如果把一个软件系统看成许多模块的组合，那么每个模块都有自己的局部目标：这个函数要做什么，这个类要暴露什么方法，这个接口要返回什么结构。但软件工程真正关心的是系统级目标：

- 能否编译？
- 单测是否通过？
- 集成测试是否通过？
- 是否破坏旧功能？
- 是否符合接口契约？
- 是否满足安全要求？
- 性能是否退化？
- 未来是否容易维护？

模型在局部上下文里看到的，往往只是其中很小的一部分。

它可能只看到当前函数签名，看不到调用链；只看到一个文件，看不到跨文件依赖；只看到报错信息，看不到历史设计原因；只看到当前需求描述，看不到隐含的业务约束；只看到测试失败，看不到测试本身是否充分。

于是它会退回到训练语料中最常见、最像样、最容易补全的模式。

这种模式可能在别的项目里成立，在当前项目里却不成立。它可能在简单 demo 里成立，在真实系统里却不成立。它可能在 happy path 上成立，在异常路径、并发场景、灰度发布和数据迁移中却不成立。

这就是模块化局部最优幻觉的本质：模型没有真正拿到全局目标，却给出了一个局部上很顺滑的答案。

如果说传统软件工程中的复杂性来自人类无法完全理解系统，那么 AI Coding 并没有消灭这种复杂性。它只是把复杂性从“写代码”转移到了“判断生成出来的代码是否真的属于这个系统”。



### 幻觉并不只是“不知道”

谈到幻觉时，很多人会把它理解成模型不知道某件事，于是胡乱编造。

这当然是一部分原因。训练数据里没有，或者相关知识太长尾，模型确实很难稳定记住。API 版本更新、依赖库变化、内部私有代码、公司业务规则，这些都不可能完整存在于模型参数中。

但在 Coding 场景中，还有另一种更麻烦的情况：模型不是完全不知道，而是知道一部分。

它知道某个框架大概怎么用，知道某种设计模式大概长什么样，知道某类错误通常怎么修，知道某个语言的常见写法。正因为它知道一部分，所以它生成的答案更像真的。

例如模型知道 Kubernetes Controller 通常会有 Reconcile 方法，也知道需要处理 finalizer、status、event、retry。但如果它不知道当前项目是如何封装 client、如何做幂等、如何处理状态迁移、如何记录审计日志，那么它可能生成一段“看起来很 Kubernetes”的代码，却破坏了项目原有的控制面约束。

这类错误比完全不会更难发现。

完全不会时，模型可能会生成明显不编译的代码；知道一部分时，它会生成能通过第一眼审查的代码。它会使用正确的术语、正确的目录结构、正确的命名风格，甚至看起来符合项目的抽象，但内部关键约束是错的。

这有点像一个刚入职的工程师，读过几篇内部文档，模仿了项目风格，然后提交了一个很像样的 PR。问题在于，他还没有理解那些没有写在文档里的边界：为什么这里不能直接重试，为什么这个状态迁移必须 CAS，为什么这个资源删除前必须先释放租约，为什么这个接口不能在事务里做远程调用。

AI Coding 的幻觉，很多时候就是这种“半理解”。



### 复杂性没有消失，只是被转移了

《没有银弹》中最重要的观点是，软件工程的根本复杂性不会被某种工具彻底消灭。高级语言、设计模式、微服务、云原生、低代码都曾在某个阶段被寄予厚望，但它们最终都不是银弹。

它们确实解决了一部分问题，也确实提升了开发效率。但它们同时引入了新的复杂性。

高级语言屏蔽了机器细节，却带来了运行时、抽象泄漏和性能问题；微服务拆分了单体复杂性，却带来了网络、治理、观测、部署和一致性问题；云原生降低了资源管理门槛，却把复杂性沉入 Kubernetes、Service Mesh、CI/CD 和可观测性系统中。

AI Coding 也是如此。

它吞噬了显性的复杂性：写样板代码、查 API、生成测试、解释报错、迁移简单逻辑。这些事情确实变快了。过去开发者要花几个小时写出的东西，现在可能几分钟就能得到一个初稿。

但它制造了隐性的复杂性：

- 代码 Review 的成本上升了，因为生成代码数量变多了。
- 信任边界变模糊了，因为输出看起来很专业。
- 错误来源更难追踪了，因为模型不会像人类一样保留清晰的设计意图。
- 技术债更容易被批量制造，因为低成本生成降低了提交代码的心理门槛。
- 工程师的职责从“写实现”转向“验证实现”，但验证能力并没有自动增强。

这也是为什么我不太认同“AI 会让程序员不再重要”的说法。更准确地说，AI 会改变程序员的重要性所在。

过去程序员的价值很大一部分体现在：能不能把需求翻译成代码。未来这部分价值会被压缩。但另一部分价值会变得更重要：能不能判断一段代码是否符合系统目标，能不能设计出可靠的验证闭环，能不能识别模型输出背后的隐含风险，能不能在复杂系统中保持清醒。

AI 可以让写代码变快，但它不会自动让系统变简单。



### 为什么测试不足会放大幻觉？

在 AI Coding 中，测试是最常见的安全感来源。

让模型写代码，然后跑测试。如果测试通过，似乎就说明问题解决了。这种工作流当然比直接复制粘贴模型输出要可靠得多，但它依然有一个前提：测试本身足够代表真实需求。

现实中这个前提经常不成立。

单测只能覆盖被写出来的场景，没写出来的边界条件不会自动出现；集成测试通常成本更高，覆盖率更低；性能测试、安全测试、回归测试更容易被忽略；而真实业务中的历史兼容、数据脏值、异常流、并发交错，往往不是一个简单测试文件能表达清楚的。

这就导致一种很危险的情况：模型生成的代码通过了局部测试，于是它获得了“看起来正确”的证据，但系统级风险仍然存在。

这和 RAG 中的检索问题有点类似。很多人以为给模型加上外部知识库就能解决幻觉，但如果检索出来的内容是错的、过时的、片面的，模型只会基于错误上下文生成更自信的答案。测试也是如此。如果验证器本身不完整，它只能证明“没有被这些测试打败”，不能证明“真的正确”。

所以 AI Coding 的关键不只是让模型生成代码，而是要让生成代码进入尽可能接近真实系统目标的验证链路。

编译器、类型检查器、lint、单测、集成测试、回归测试、安全扫描、性能基准、人工 Review，它们本质上都是把模型的局部概率输出拉回工程现实的锚点。

如果没有这些锚点，AI Coding 很容易变成一种更快制造不确定性的方式。



### 我们应该如何使用 AI Coding？

如果承认 AI Coding 中的幻觉无法彻底消灭，那么问题就不再是“要不要用 AI”，而是“在什么边界内使用 AI”。

我更倾向于把 AI Coding 看成一个强大的候选生成器，而不是一个可以直接信任的工程决策者。

它很适合做这些事情：

1. 生成初稿。
2. 补全样板代码。
3. 解释陌生代码。
4. 根据错误日志提出排查方向。
5. 生成测试用例草案。
6. 总结文档和接口用法。
7. 对已有实现提出可能的边界条件。

但它不应该在没有验证的情况下直接承担这些事情：

1. 修改核心交易链路。
2. 改动权限、安全、加密相关代码。
3. 自动合并大规模重构。
4. 在缺少测试的历史仓库中批量修复问题。
5. 对复杂并发、分布式一致性、资源生命周期做最终判断。
6. 在不了解业务语义的情况下设计关键抽象。

更可靠的工作流应该是：

1. 先澄清需求，而不是直接写代码。
2. 让模型阅读相关文件，而不是只看当前报错。
3. 要求模型先给出计划，而不是马上修改。
4. 让模型说明影响范围和假设条件。
5. 生成代码后必须运行编译、测试和静态检查。
6. 对失败结果进行迭代，而不是让模型凭空“再试一次”。
7. 最后由人类做系统级 Review。

其中最重要的一点是：把 AI 接到验证器上。

这比单纯换更强的模型更现实。模型越强，局部输出当然会越好，但只要它仍然无法完整拥有系统事实和系统目标，幻觉就不会消失。验证器的意义在于，它把“像真的”变成“被检查过”。

一个没有验证器的 Coding Agent，更像是一个自信的实习生；一个接入仓库检索、类型系统、测试、日志和人工 Review 的 Coding Agent，才更接近真正可用的工程助手。



### 对开发者意味着什么？

AI Coding 会改变开发者的学习路径。

过去学习一门语言，通常要从语法、标准库、框架、项目结构逐步推进。现在 AI 可以直接生成大量示例，让学习者更快获得反馈。这是好事，它降低了启动成本。

但也有另一面：如果开发者过早把思考外包给 AI，很容易只获得“能跑的答案”，却没有建立自己的判断体系。

这就像写作一样。如果每一个想法都交给 AI 扩写，短期内确实能得到更多文字，但长期看可能失去训练思考的机会。Coding 也是如此。如果每一个实现都交给 AI，开发者可能会更快完成任务，却更慢理解系统。

未来工程师的核心能力可能会从“记住 API”转向下面这些：

- 能否描述清楚问题。
- 能否拆分复杂需求。
- 能否设计验证标准。
- 能否识别模型输出中的不确定性。
- 能否理解系统边界和历史约束。
- 能否在效率与可靠性之间做权衡。

也就是说，AI 并没有让基础能力不重要，反而让基础能力更像一种过滤器。

没有基础能力的人，可能会被 AI 的流畅输出带着走；有基础能力的人，则能把 AI 当作放大器。

这大概也是 AI Coding 最真实的样子：它不是替代思考，而是放大思考。它会放大一个人的表达能力、抽象能力、验证能力，也会放大一个人的偷懒、草率和盲目信任。



### 后记

我最初接触 AI Coding 时，也很容易被它的即时反馈吸引。它能快速补齐一些知识缺口，也能在学习新语言、新框架时提供很好的陪伴感。相比搜索引擎，它更像一个耐心的对话者；相比文档，它更愿意顺着你的问题展开。

但使用得越多，就越能感受到它的边界。

它能写出代码，却未必理解这个系统为什么这样设计；它能修复当前错误，却未必知道这个错误背后是否还有更深的抽象问题；它能生成一个庞大的 PR，却不能替你承担这段代码未来在线上运行的责任。

也许 AI Coding 最值得警惕的地方，不是它会犯错，而是它会以一种非常流畅、非常专业、非常节省时间的方式犯错。

这正是幻觉在软件工程中的危险之处。

它不是让机器说胡话，而是让机器生成一段看起来可以工作的复杂性。开发者如果只看到效率提升，就容易忽略复杂性并没有消失，只是换了一种形式重新回到了系统里。

所以，与其追问 AI Coding 能不能彻底消灭幻觉，不如接受一个更工程化的答案：不能彻底消灭，但可以被约束、被验证、被隔离、被持续压低。

真正可靠的 AI Coding，不是让模型一次性给出完美答案，而是建立一套闭环：澄清问题，补充上下文，生成计划，编写代码，执行验证，修复错误，审查风险。

在这个闭环里，AI 是强大的工具，但不是最终的责任主体。

最终负责的依然是人。

而软件工程的历史似乎也总是在提醒我们：每一种新工具都会改变复杂性的形态，但不会让复杂性凭空消失。高级语言如此，微服务如此，云原生如此，AI Coding 也不会例外。

它不是银弹。

但如果使用得当，它确实是一把足够锋利的工具。
